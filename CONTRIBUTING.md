## 1. Быстрый старт для контрибьютора

```bash
git clone https://github.com/Almight71/password-generator.git
cd password-generator
npm install            # один раз: ставит jsdom для интеграционных тестов

# проверить, что всё зелёное
node --check src/js/utils.js
npm test               # 25/25 — вот ваш baseline

# поднять приложение
npm start              # → http://localhost:8080
```

Откройте `tests/unit-tests.html` в браузере — удобный способ смотреть на
прогон логики без терминала.

## 2. Как устроен проект

Читать обязательно, иначе правки поломают скрытые контракты:

| Правило | Почему |
|---|---|
| `generator.js` и `storage.js` **не должны обращаться к DOM** | на этом построены unit-тесты в Node |
| Порядок `<script>` в HTML не менять | `utils → generator → storage → ui → app` |
| Всё, что попадает в разметку, проходит `escapeHtml()` | иначе возвращается XSS |
| Входные данные проходят `validateName` / `sanitizeInput` | плюс защита от `null`/`undefined` |
| Каждая операция ввода-вывода в `try/catch` | принцип: падение недопустимо, деградация — допустима |
| JSDoc на **каждой** публичной функции | это и документация, и контракт |

Стиль кода, ADR и журнал исправлений: [docs/SDLC/04_DEVELOPMENT.md](docs/SDLC/04_DEVELOPMENT.md).

## 3. Цикл работы над изменением

1. **Issue.** Сначала заведите issue (или найдите существующий) — чтобы
   обсудить подход до написания кода. Для мелких правок документации
   шаг можно пропустить.
2. **Ветка.** `feature/<короткое-описание>` или `fix/<номер-issue>`.
3. **Тест первым.** Добавьте регрессионный кейс в `tests/test-suite.js`
   до или вместе с исправлением. Фикс без теста не принимается.
4. **Код.** Следуйте существующему стилю: 2 пробела, `const` по умолчанию,
   русские комментарии и сообщения об ошибках.
5. **Проверка.**
   ```bash
   for f in src/js/*.js tests/*.js; do node --check "$f" || exit 1; done
   npm test
   ```
6. **Документация.** Обновите README / API / SDLC-документы, если менялось
   поведение, схема хранилища или публичный контракт.
7. **PR.** Заполните шаблон (см. §5), укажите, какие требования покрыты.

## 4. Правила приёмки

Pull request будет принят, если:

- [ ] `npm test` даёт 25/25 (или больше — новые кейсы добавлены)
- [ ] `node --check` проходит для всех JS-файлов
- [ ] Добавлен регрессионный тест к исправлению дефекта
- [ ] `CHANGELOG.md` дополнен в разделах «Добавлено» / «Исправлено»
- [ ] Нет `console.log` с отладочным мусором (допустимы
      `console.debug/info/warn/error` с префиксом `[DEBUG]/[INFO]/[WARN]/[ERROR]`)
- [ ] Нет секретов, токенов и путей локальной машины
- [ ] Изменения не ломают раскладку на 320 / 768 / 1920 px
      (при визуальных правках — переснимите скриншоты: `npm run screenshots`)

**Размер PR.** Предпочтительны изменения до ~300 строк. Большие задачи
разбейте на серии коммитов, каждый из которых оставляет проект рабочим.

## 6. Сообщение о проблеме

В [Issues](https://github.com/Almight71/password-generator/issues) указывайте:

| Поле | Что писать |
|---|---|
| Что ожидалось | конкретное поведение |
| Что произошло | фактическое поведение + текст ошибки |
| Шаги | пошаговый сценарий воспроизведения |
| Окружение | ОС, браузер и его версия, `file://` или `http://` |
| Данные | можно ли воспроизвести на пустом `localStorage` |
| Консоль | что показывает DevTools → Console |

**Проблемы безопасности** помечайте в теме меткой `security` — они
разбираются в приоритете. Ограничения, которые приняты осознанно,
перечислены в [docs/SDLC/07_MAINTENANCE.md §5](docs/SDLC/07_MAINTENANCE.md).

## 7. Добавление функции

Перед началом — три вопроса:

1. **Соответствует ли это рамкам продукта?** Генератор, хранилище, документация
   по SDLC — в рамках. Синхронизация, аккаунты, автозаполнение форм — нет
   (см. «Вне рамок» в [01_REQUIREMENTS.md](docs/SDLC/01_REQUIREMENTS.md)).
2. **Где точка расширения?** В большинстве случаев таблица в
   [ARCHITECTURE.md §12](docs/ARCHITECTURE.md) уже подсказывает минимальный
   набор файлов.
3. **Нужна ли миграция данных?** Если меняется схема записи — добавьте
   миграцию и поднимите версию ключа хранилища (`passwords_v1` → `v2`),
   не забыв тест на перенос.

Дорожная карта: [docs/SDLC/07_MAINTENANCE.md §4](docs/SDLC/07_MAINTENANCE.md).
Если ваша идея уже там — напишите об этом в issue, чтобы не дублировать усилия.

## 8. Документация

Проект живёт за счёт документации. Любое изменение поведения требует
правки хотя бы одного из:

| Файл | Когда обновлять |
|---|---|
| `CHANGELOG.md` | всегда |
| `docs/API.md` | меняется публичный контракт |
| `docs/ARCHITECTURE.md` | меняются слои, потоки, схема данных |
| `docs/USER_GUIDE.md` | меняется то, что видит пользователь |
| `docs/SDLC/0X_*.md` | меняется процесс или его артефакты |
| `tests/test-cases.md` | добавляются или меняются кейсы |

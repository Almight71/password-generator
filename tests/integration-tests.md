# Интеграционные тесты

**Проект:** Password Generator with Storage
**Кейсы:** TC18–TC22
**Окружение:** jsdom 24.1.3 + реальные `src/index.html` и `src/sdlc_cycle.html`
**Результат прогона:** все 5 ✅ PASS (см. [test-report.md](test-report.md))

Интеграционные тесты проверяют **взаимодействие модулей**, а не изолированные
функции. В отличие от unit-тестов здесь загружается настоящая HTML-страница
со всеми `<script>`, приложение инициализируется обработчиком `DOMContentLoaded`
и тестируется так, как им пользуется человек.

---

## 1. Общая организация

### 1.1. Подготовка окружения

`tests/run-tests.js`:

1. читает HTML-файл с диска;
2. `JSDOM.fromFile(file, { runScripts: 'dangerously', resources: 'usable' })`;
3. в `beforeParse` подставляет `crypto` (jsdom его не реализует),
   `document.execCommand` и `Element.prototype.scrollIntoView`;
4. ждёт события `load` + 50 мс для отработки инициализации;
5. проверяет, что глобальный `window.app` создан.

### 1.2. Что можно и чего нельзя делать в интеграционном тесте

| Допустимо | Недопустимо |
|---|---|
| Вызывать публичные методы `window.app` | Подменять внутренние поля `PasswordApp` |
| Симулировать события (`dispatchEvent`, `.click()`) | Менять CSS и проверять раскладку (это работа TC23–25) |
| Читать `document` и проверять узлы | Ожидать реальной асинхронности сети (её нет) |
| Подставлять записи напрямую в `storage.cache` для проверки защиты | Зависеть от предыдущего кейса (каждый кейс приходит в чистое состояние) |

### 1.3. Изоляция

- хранение подменено на `MemoryStore` (jsdom не даёт устойчивый `localStorage`);
- каждый кейс начинается с явного `storage.clear()` или создаёт записи заново;
- после TC20 хранилище очищается в конце самого кейса, чтобы не оставить
  враждебные записи для последующих проверок.

## 2. TC18 · Полный цикл «генерация → сохранение»

**Цель.** Убедиться, что после `DOMContentLoaded` приложение полностью
работоспособно: первый пароль сгенерирован, а путь «ввод названия →
`saveCurrent()` → таблица → счётчик» замкнут.

| # | Шаг | Проверка |
|---|---|---|
| 1 | `window.app` определён | инициализация прошла без ошибок |
| 2 | `#password` содержит 16 символов | `generate()` отработал в `init()` |
| 3 | В `#passwordName` вписать «Test Service» | |
| 4 | Вызвать `app.saveCurrent()` | возвращён объект с числовым `id` |
| 5 | `app.storage.count() === 1` | запись легла в хранилище |
| 6 | `#passwordsList tbody tr` → 1 строка | `renderTable` отрисовал запись |
| 7 | Строка содержит «Test Service» | название попало в разметку |
| 8 | `#passwordsCount` содержит «1» | счётчик обновлён |
| 9 | `#passwordName` пуст | поле очищено после успеха |

**Что ломалось бы здесь:** порядок вызовов в `saveCurrent()`,
очистка поля при неудаче, пересчёт счётчика, перерисовка таблицы
(все — разные модули: `app.js`, `storage.js`, `ui.js`).

## 3. TC19 · Поиск

**Цель.** Проверить связку `#searchBox` → `PasswordApp.query` →
`PasswordStorage.search` → перерисовка таблицы и счётчика.

| # | Шаг | Проверка |
|---|---|---|
| 1 | Сохранить `Gmail`, `Telegram`, `Bank Alpha` | 3 строки, счётчик «Всего: 3» |
| 2 | `searchBox.value = 'gma'` + событие `input` | остаётся 1 строка |
| 3 | `#passwordsCount` → `Найдено: 1 из 3` | счётчик различает полный и отфильтрованный набор |
| 4 | Очистить поле + `input` | возвращаются все 3 строки |

**Важная деталь:** событие шлётся именно `input`, а не `change` — так настроены
слушатели в `bindEvents()`; расхождение сломало бы реальный пользовательский
ввод, но не наш тест, если бы он тоже слушал `change`.

## 4. TC20 · XSS через скомпрометированное хранилище

**Цель.** Проверить защиту на **последнем рубеже** — при отрисовке, —
когда валидация входа обошена.

Сценарий осознанно нереалистичен на первом шаге и реалистичен на втором:

```
1. Атакующий (или баг) положил в localStorage запись
   с name  = '<img src=x onerror=window.__xss=1>&"'
   и password = '<script>window.__xss=1</script>'
2. app.render() строит строку таблицы
3. Если escapeHtml отсутствует — <img> исполнится немедленно
4. Если escapeHtml неполный (нет &) — атрибуты разъедутся
```

| # | Проверка | Результат |
|---|---|---|
| 1 | `#passwordsList img` → 0 элементов | ✅ |
| 2 | `#passwordsList script` → 0 элементов | ✅ |
| 3 | `window.__xss === undefined` | пейлоад не выполнился ✅ |
| 4 | Текст `img src=x` присутствует как текст | запись не потеряна, а экранирована ✅ |

**Почему запись вставляется в `storage.cache`, а не через `add()`:**
`add()` вызывает `validateName` → `sanitizeInput`, и пейлоад не доживёт
до отрисовки. Тест проверяет именно `renderRow()` + `escapeHtml()`.

Почему этого достаточно: `renderRow()` — единственная точка, где данные
хранилища попадают в разметку. Закрыв её, закрывается весь вектор.

## 5. TC21 · Удаление с модальным подтверждением

**Цель.** Проверить асинхронный поток `UIManager.confirm()` → `Promise`
и корректное поведение обоих исходов.

```
app.deleteRecord(id)          →  Promise<boolean>
   │
   ├─ click [data-confirm-reject]   →  resolve(false)
   │      запись остаётся, count = 1
   │
   └─ click [data-confirm-accept]   →  resolve(true)
          запись удаляется, count = 0, пустое состояние
```

| # | Шаг | Проверка |
|---|---|---|
| 1 | Создать запись «ToDelete» | count = 1 |
| 2 | `deleteRecord(id)` → клик **Отмена** | `false`, count = 1 |
| 3 | `deleteRecord(id)` → клик **Удалить** | `true`, count = 0 |
| 4 | Текст таблицы | содержит «Нет сохранённых» |

**Асинхронность:** тест возвращает `Promise` из `run()` — раннер `await`-ит его.
Синхронный тест на этот поток падал бы с гонкой.

Побочно проверяется, что фокус возвращается на прежний элемент
(`previousFocus.focus()` в `confirm()`), иначе следующий Enter
после отмены удалил бы запись без подтверждения.

## 6. TC22 · Диаграмма SDLC

**Цель.** Убедиться, что интерактивная диаграмма поддерживает
семь состояний и синхронизирует три связанных представления:
узлы SVG, точки прогресса и панели описания.

| # | Шаг | Проверка |
|---|---|---|
| 1 | `[data-panel]` → 7 штук | все 7 этапов описаны |
| 2 | `data-panel="0"` видима | первый этап открыт по умолчанию |
| 3 | Клик по `.phase-node[data-phase="4"]` | панель 4 открыта, панель 0 закрыта |
| 4 | `aria-pressed="true"` на активном узле | доступность актуальна |
| 5 | `aria-selected="true"` на точке `data-phase="4"` | точки синхронизированы |
| 6 | Ровно 1 `.phase-node.is-active` | нет «двойной» активации |
| 7 | `#nextPhase` → панель 5 | навигация вперёд |
| 8 | `#prevPhase` ×2 → панель 3 | переход назад не «застревает» на нуле |

Последний пункт отдельно ловит классическую ошибку граничного условия
`Math.max(0, current - 1)` — если бы шаг назад от этапа 0 «зацикливался»
на 0, переход с 0 на последний этап дал бы неверный индекс.

## 7. Как воспроизвести вручную

```bash
npm install
npm test          # запускает TC18–TC22 автоматически
```

Чтобы посмотреть на страницы глазами:

```bash
npm start                     # http://localhost:8080
# открыть http://localhost:8080/  и  http://localhost:8080/sdlc_cycle.html
```

Или откройте [unit-tests.html](unit-tests.html) — там же, что и в раннере,
но только логическая часть; интеграционные кейсы требуют jsdom и потому
доступны только через `npm test`.

## 8. Ограничения

| Ограничение | Влияние | Компенсация |
|---|---|---|
| jsdom не реализует layout | реальные переносы и прокрутка не проверяются | TC23–25 + ручной обзор PNG |
| jsdom не реализует Clipboard API | копирование не покрыто | ручной сценарий M1 |
| `KeyboardEvent` не двигает фокус | навигация стрелками не проверяется | ручной сценарий M4 |
| Нет настоящего `localStorage` | поведение приватного режима не эмулируется | TC16/TC17 + MemoryStore |
| Нет нескольких браузеров в CI | расхождения движков не ловятся автоматически | документированные поддерживаемые браузеры (NFR4) |
